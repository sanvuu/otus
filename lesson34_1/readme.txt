# Домашнее задание: Настройка VPN (TUN/TAP, OpenVPN RAS)

## 1. Текст задания
1. Настроить VPN между двумя ВМ (`server` и `client`) в режимах `tun` и `tap`, замерить скорость в туннелях, сделать вывод об отличающихся показателях.
2. Поднять RAS (Remote Access Server) на базе OpenVPN с клиентскими сертификатами, подключиться с локальной хост-машины на ВМ.
3. (*) Самостоятельно изучить и настроить `ocserv`, подключиться с хоста к ВМ.

**Формат сдачи:** `Vagrantfile` + `Ansible` + документация в `README.md`.

## 3. Особенности проектирования и реализации решения

### Инфраструктура и автоматизация
* **Стек:** Вместо связки VirtualBox + Ubuntu 22.04 использован гипервизор **KVM/Libvirt** на хосте **Ubuntu 26.04** и актуальный образ **`bento/ubuntu-24.04`**.
* **Идемпотентный Ansible-плейбук (`playbook.yml`):**
  * Автоматически устанавливает `openvpn`, `iperf3` и `easy-rsa` на узлы.
  * Генерирует статический ключ (`static.key`) для P2P-туннеля и распространяет его между `server` и `client`.
  * Реализовано быстрое переключение между режимами `tun` и `tap` через переменную `vpn_mode` (`-e "vpn_mode=tap"`).
  * Для RAS-сервера в неинтерактивном режиме (`--batch`) разворачивает PKI на базе `easy-rsa`, выпускает корневой CA, сертификаты/ключи сервера и клиента, генерирует параметры Диффи-Хеллмана (`dh.pem`) и ключ `tls-crypt` (`ta.key`).
  * Автоматически выгружает готовый клиентский пакет (`client.conf`, `ca.crt`, `client.crt`, `client.key`, `ta.key`) на хост в директорию `./ras_client_bundle/`.

### Адаптация конфигураций под OpenVPN 2.6 (Ubuntu 24.04)
При переносе инструкций из методички на OpenVPN 2.6 были внесены следующие исправления:
1. **Штатные systemd-юниты:** Вместо создания кастомного `openvpn@.service` использован встроенный юнит `openvpn-server@.service` с размещением конфигураций в `/etc/openvpn/server/` (это позволило запустить P2P-туннель `openvpn-server@p2p` и RAS-сервер `openvpn-server@ras` параллельно без конфликтов).
2. **Адресация P2P в режиме `tun`:** В OpenVPN 2.6 директива `topology subnet` несовместима с режимом статического ключа (`--secret`). Для `tun` задана явная точка-точка адресация (`ifconfig 10.10.10.1 10.10.10.2` и зеркально на клиенте), а для `tap` — адрес с маской (`ifconfig 10.10.10.1 255.255.255.0`).
3. **Устранение петли маршрутизации:** Из конфига P2P-клиента удалена директива `route 192.168.56.0 255.255.255.0`, так как IP-адрес сервера (`192.168.56.10`) принадлежит этой же подсети, и заворачивание её в туннель приводило к зацикливанию трафика.
4. **Современное шифрование и MTU:** Устаревшее сжатие `comp-lzo` заменено на `AES-256-CBC` (в P2P) и `AES-256-GCM` + `tls-crypt` (в RAS). Добавлен параметр `mssfix 1360` для исключения фрагментации TCP-сегментов при нагрузочном тестировании через `iperf3`.

## 4. Замеры скорости (`iperf3`) и выводы

### Результаты тестирования (40 секунд, интервал 5 секунд)

| Режим | Уровень модели OSI | Средний Bitrate (`sender` / `receiver`) | Передано данных за 40 с | Ретрансмиты (Retr) |
| :--- | :--- | :--- | :--- | :--- |
| **TUN** | L3 (сетевой, IP-пакеты) | **479 / 478 Мбит/с** | 2.23 ГБ | 2932 |
| **TAP** | L2 (канальный, Ethernet-кадры) | **493 / 492 Мбит/с** | 2.29 ГБ | 1203 |

### Выводы о режимах TUN и TAP
1. **Производительность:** На изолированном виртуальном стенде пропускная способность обоих режимов практически идентична (~480–493 Мбит/с) и ограничивается производительностью одного потока vCPU (так как классический OpenVPN в user-space обрабатывает шифрование в один поток). Небольшая разница в ~14 Мбит/с находится в пределах погрешности планировщика CPU гипервизора, при этом накладные расходы (overhead) на каждый пакет в режиме `tun` ниже за счет отсутствия L2-заголовков Ethernet (14–18 байт).
2. **Область применения:**
   * **`TUN` (L3)** — оптимален для большинства задач (связывание офисов/подсетей, удаленный доступ RAS, мобильные клиенты). Он маршрутизирует только IP-пакеты и отсекает широковещательный (broadcast) трафик, не засоряя реальные WAN-каналы.
   * **`TAP` (L2)** — эмулирует полноценный сетевой Ethernet-адаптер. Необходим только тогда, когда требуется объединить удаленные сегменты в единый L2-мост (bridge) или передавать не-IP протоколы (ARP, DHCP, NetBIOS). В крупных сетях создает избыточную нагрузку из-за передачи broadcast-трафика.

## 5. Проверка работы и полезные заметки

### Команды для воспроизведения
```bash
# 1. Поднятие ВМ и автоматическая настройка через Ansible (по умолчанию режим tun)
vagrant up --provider=libvirt

# 2. Замер скорости в режиме TUN
vagrant ssh client -c "iperf3 -c 10.10.10.1 -t 40 -i 5"

# 3. Переключение стенда на режим TAP и замер скорости
ansible-playbook -i .vagrant/provisioners/ansible/inventory/vagrant_ansible_inventory playbook.yml -e "vpn_mode=tap"
vagrant ssh client -c "iperf3 -c 10.10.10.1 -t 40 -i 5"

# 4. Подключение с хоста к RAS-серверу (Задание 2)
cd ras_client_bundle
sudo openvpn --config client.conf
```

### Проверка маршрутизации на хосте при подключении к RAS
При запуске клиента на хосте (OpenVPN 2.7 с поддержкой ядерного ускорения `ovpn-dco`) успешно устанавливается TLSv1.3-сессия, создается интерфейс `tun0` (`10.20.20.6 peer 10.20.20.5`), и в таблицу маршрутизации добавляется сеть `10.20.20.0/24`:
```text
\$ ip r | grep 10.20.20
10.20.20.0/24 via 10.20.20.5 dev tun0 metric 200
```
