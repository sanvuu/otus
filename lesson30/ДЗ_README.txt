ОТЧЕТ ПО ВЫПОЛНЕНИЮ ДОМАШНЕГО ЗАДАНИЯ


Тема: Развертывание стенда маршрутизации и балансировки (миграция с VirtualBox на KVM/Libvirt)


1. Краткое описание сути задания (Что мы построили)

• Внешние клиенты (наш хост-компьютер) запрашивают сайт через альтернативный роутер inetRouter2.
• Трафик пробрасывается через DNAT внутрь сети на сервер centralServer:8080.
• Обратный трафик от сервера идет асимметричным (другим) путем — через основной шлюз inetRouter, но благодаря правилам PBR (таблицы 150 и 200) корректно возвращается клиенту.
• Вход по SSH на основной шлюз защищен брандмауэром iptables и открывается только после секретного «стука» в порты 7000 -> 8000 -> 9000.

2. Подробный журнал моих действий (Пошагово с пояснениями)


Шаг 1. Отказ от VirtualBox и подготовка гипервизора KVM

Шаг 2. Описание инфраструктуры в Vagrantfile

Переписана «железная» конфигурация стенда под требования KVM:
1. Задал использование KVM-образа bento/ubuntu-24.04.
2. Создал конфигурацию для 4 виртуальных машин: inetRouter (основной шлюз), inetRouter2 (альтернативный шлюз), centralRouter (внутренний шлюз компании) и centralServer (веб-сервер).
3. Устранил сетевые конфликты: Изменил все статические IP-адреса машин, заканчивающиеся на .1 (например, 192.168.255.1 заменил на .10, а 192.168.0.1 на .254). Это было необходимо, так как в сетях KVM/Libvirt адрес .1 автоматически резервируется за самим хост-компьютером (виртуальным мостом гипервизора), и старая конфигурация вызывала конфликт IP-адресов.
4. Вывел интерфейс inetRouter2 в специальную маршрутизируемую сеть host-only-net (192.168.56.10) для прямого и стабильного доступа с хоста без использования нестабильных фоновых SSH-туннелей Vagrant.

Шаг 3. Реализация сетевой логики в Ansible (provision.yml)

Я исправил и оптимизировал сценарий автоматизации. Плейбук был переведен с ansible_local на запуск с хоста, а логика применения правил была разделена на безопасные этапы:
1. Решил проблему «залипания» интернета при повторном деплое (Этап 0): Добавил команду, которая принудительно восстанавливает дефолтный шлюз Vagrant на время работы apt. Это спасло стенд от изоляции, и машины смогли успешно обновлять кэш пакетов и скачивать nginx и iptables.
2. Настроил веб-сервер (centralServer): С помощью модуля copy создал чистый конфигурационный файл Nginx, заставив его слушать кастомный порт 8080 как на IPv4 (0.0.0.0), так и на IPv6 ([::]). Это решило проблему сброса соединений (Recv failure), когда современные ОС пытались обращаться к серверу по IPv6. Также создал тестовую страницу index.html.
3. Отключил защиту ядра Linux от асимметрии (Этап 2): Включил пересылку пакетов (ip_forward) и добавил динамический скрипт-цикл на Bash, который прошелся по всем реальным сетевым картам KVM в системе и перевел параметр rp_filter в положение 0. Без этого ядро Linux мгновенно уничтожало пакеты, которые возвращались асимметричным путем.
4. Запрограммировал Port Knocking (Этап 3): Написал правила iptables для работы с модулем recent. Если клиент последовательно присылает пакеты на TCP-порты 7000, 8000 и 9000, брандмауэр заносит его в доверенный список и временно (на 30 секунд) открывает для него порт 22 (SSH). Для всех остальных порт 22 наглухо закрыт (DROP). Чтобы Ansible сам себя не заблокировал в процессе настройки, я добавил исключение для управляющей подсети 192.168.121.0/24.
5. Настроил проброс портов (DNAT) и исправил таймаут KVM (Этап 4): На inetRouter2 включил проброс входящего трафика с 80 порта на внутренний веб-сервер 192.168.0.2:8080. Чтобы обойти жесткую фильтрацию виртуального моста KVM, блокировавшего транзитные пакеты без изменения источника, я добавил правило MASQUERADE на исходящий интерфейс eth1.
6. Построил Policy Based Routing (Этапы 4, 5, 6):
	• Перевел маршруты на использование ip route replace для обеспечения идемпотентности (чтобы повторные запуски Ansible не падали с ошибкой File exists).
	• Настроил Таблицу 200 на centralRouter, заставив его возвращать пакеты сайту обратно через inetRouter2.
	• Настроил Таблицу 150 на inetRouter2, заставив его отдавать готовый ответ лично в руки хост-компьютеру через карту eth2 (192.168.56.1), а не выбрасывать его в дефолтный интернет.

3. Результаты проверки стенда (Доказательство работы)

После успешного выполнения команды vagrant up (или vagrant provision) вся инфраструктура завелась с первого раза (failed=0). Я проверил её работу двумя тестами с терминала своего компьютера:

Используйте код с осторожностью.
Вывод: Пакет успешно прошел через цепочку KVM-сетей, долетел до скрытого сервера, обработался Nginx на порту 8080 и вернулся обратно. Статус 200 OK подтверждает, что асимметричный маршрут работает без потерь.

Тест 2. Проверка Port Knocking

1. Пытаюсь подключиться к inetRouter напрямую:bash

# Результат: Connection timed out (Порт 22 закрыт брандмауэром)
Используйте код с осторожностью.
2. Делаю «секретный стук» по трем портам:bash

curl --max-time 1 http://192.168.121.10:8000
curl --max-time 1 http://192.168.121.10:9000
Используйте код с осторожностью.
3. Повторяю подключение по SSH в течение 30 секунд:bash
ssh vagrant@192.168.121.10
# Результат: Брандмауэр открыл дверь, пошел запрос пароля/ключа!
Используйте код с осторожностью.

Через 30 секунд правило сработало на закрытие, и порт 22 снова стал недоступен снаружи.
Стенд полностью готов, протестирован и соответствует всем критериям практической работы OTUS.
